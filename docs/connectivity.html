05 / Connectivity

Bearers, carriers, adapters

Adding every protocol to the FASP core would duplicate authorization, framing and storage once per ecosystem. Instead each source terminates at a small adapter and enters the same signed path. This page tells you which is which — and which ones this repository actually implements.

01

The selection rule. Use HTTPS for reliable control and low-rate packets on any IP carrier. Use WebSocket when a paired peer needs lower-latency bidirectional push. Use Bluetooth when IP is unavailable and both hosts support the radio profile. Use a gateway for fieldbuses, broker ecosystems, and devices that cannot sign for themselves. Route sustained data through a leased stream and send the control that opens and closes it as a reliable packet.

The pipeline diagram is the reason the adapter concept is not a compromise. An already-signed FASP envelope is verified as received. A gateway for an unsigned device must validate the device-specific data and sign a new envelope with the gateway's own identity, preserving the original source as provenance — because pretending an unsigned device is a paired FASP peer would be a lie the policy engine would have to believe.

02

Three labels, and the difference matters. Native means this repository implements the bearer. IP carrier means the operating system gives you a routable IP link for the native HTTPS or WebSocket bearer. Adapter means a gateway or bridge is needed — listing one does not imply it is implemented.

03

The operating system supplies the network; FASP uses the endpoint it is given. Ethernet, Wi-Fi and cellular are all the same thing to this layer, which is why one bearer covers all of them.

The REST interface publishes an OpenAPI 3.1 description at /openapi.json and accepts paired, signed requests at /fasp/v1/envelopes. HTTP parsing, TLS and ALPN negotiation, and chunked encoding are handled by an audited library rather than a hand-rolled http.server — that is not a stylistic choice, it is the entire reason those paths are not where the bugs are.

The channel is an optimisation

/fasp/v1/channel is a WebSocket carrying the identical signed-envelope protocol, frame by frame, multiplexed over logical channels with per-channel grant and capability enforcement. It exists to remove a round trip from push. It is never the only copy of anything: if a push is lost, the result is still in durable state and can be pulled.

TLS posture

Use TLS 1.3 on any routable link. --tls-client-ca requires and verifies client certificates for an additional transport identity check — and is still never a substitute for envelope-level peer authorization, which runs on every request regardless of how the connection was established.

production-shaped listener
python3 -m fasp_harness serve --host 0.0.0.0 --state-dir .fasp/laptop \
  --public-url https://192.168.0.22:8766 \
  --tls-cert cert.pem --tls-key key.pem --tls-client-ca client-ca.pem \
  --rate-limit-per-peer 10 --rate-limit-burst 20 \
  --ip-rate-limit-per-second 20 --ip-rate-limit-burst 40

04

For sites with no IP at all. Two opt-in Linux listeners carry the same signed protocol over the radio — and still go through the same signature, pairing and policy checks as an HTTPS link.

Bluetooth requires an authenticated, encrypted BlueZ link in addition to FASP pairing. The two are not substitutes: the radio link proves the bytes came from the adjacent machine, FASP proves the envelope came from the system that signed it and is allowed to say this.

start a bearer, then register the peer on the other node
# serve: opt into the Classic RFCOMM listener on channel 8
python3 -m fasp_harness serve --state-dir .fasp/laptop \
  --rfcomm-channel 8

# or BLE L2CAP; choose 'random' when BlueZ reports a random LE address
python3 -m fasp_harness serve --state-dir .fasp/laptop \
  --ble-psm 0x0080 --ble-address-type random

# repeat registration on the other node with its peer address
fasp radio-register AA:BB:CC:DD:EE:FF --state-dir ~/.fasp-agent \
  --mode classic --channel 8

BLE L2CAP is the one untested path

It requires Linux, BlueZ, and Python 3.14 or newer — all three above the CI matrix, which runs 3.11 to 3.13. Treat it as implemented but unexercised, and test it on the real target radio before depending on it.

05

Finding a node grants nothing. Discovery stores a self-signed card, not a trusted peer. Authority still requires a pairing a human confirmed.

scan one explicitly named CIDR
python3 -m fasp_harness discover --cidr 192.168.0.0/24 \
  --port 8766 --state-dir .fasp/laptop

# on a production network, verify TLS properly
python3 -m fasp_harness discover --cidr 10.0.4.0/24 --scheme https \
  --ca-cert /path/to/ca.crt

One fixed path, on one explicitly supplied CIDR and port, capped at 1,024 hosts unless --allow-large is given. Obtain authorisation for a network before scanning it. This tool is not for networks you do not own or administer.

Rate limiting happens in two layers

Per-source-IP token buckets run before authentication, so an unauthenticated flood cannot reach the signature verifier. Per-peer buckets run after it, so one paired peer cannot consume the node's capacity for everyone else. Defaults are 10 requests per second per peer with a burst of 20, and 20 per second per IP with a burst of 40.

Discovery: fasp_harness/discovery.py · limits: fasp_harness/policy/ratelimit.py

06

Use adapters for adjacent ecosystems; do not reimplement them. FASP's useful combination is edge coordination, local physical-safety boundaries, uncertainty-carrying spatial state, and a stream contract that can stop forwarding when consent changes. Those are the things worth keeping small and sharp.

A2A

Task exchange, different wire

An interoperability adapter can map FASP work_items to A2A tasks while keeping one internal lifecycle. FASP is not A2A wire-compatible and does not claim to be.

AGNTCY

Sensible integration boundaries

Separating discovery, identity, schemas, messaging and observability is a reasonable stack. FASP does not need to reimplement every layer of it.

SLIM

The encryption gap, named

End-to-end group encryption is exactly what this signed-JSON transport does not provide. Useful as the reference for what a relay would need.

NATS leaf nodes

A future relay shape

An outbound-only connection from a firewalled edge site to a hub is the right pattern for device sites — a future relay here, not a current feature.

Add an ecosystem only with two things attached

An interoperability test, and a named owner for identity, policy and failure recovery. A bridge without those is a new protocol with an unowned trust model.
